# 多产品日活与启动次数：现状及统一方案

2026-09-28。状态：**源码与服务器只读核对完成；以下为实施方案，尚未合并正式统计服务。** Armor 两版页面静态化是独立、已发布的改动，不改变这里的计数口径。

## 决定与收益

建议复用现有 Go 统计实现，形成一个独立发布的轻量统计服务，供 Armor、Bomana、Calc 及后续产品接入。共用请求校验、持久化、去重、保留期和汇总能力；产品分别声明允许的指标、来源、身份口径和渠道。不把账号、地图查询或游戏遥测放进统计进程。

服务器 09:01 UTC 快照中，Armor Go 统计 RSS/PSS 为 8.68/8.68 MiB，Bomana Node 统计为 24.60/24.27 MiB，两者均 healthy。合计约 33 MiB RSS，因此本次合并主要改善维护和新增产品接入；不能承诺释放数百 MiB，也不能把候选的资源目标当成实测结果。此前删除城市库的收益已实现，不应再次计入。

## 新启动次数的已确认口径

用户确认：**每次 App 成功初始化计一次，刷新或重新打开算新启动；Launcher 页面浏览和失败重试不计。**

在成功初始化处产生一个本次启动专用的随机 `event_id`，相同上报的网络重试复用这个 ID。服务在同一事务中记录去重键并增加启动次数，重复请求返回成功但不再增加计数。它不使用“当天已上报”的 DAU 开关，所以同一安装一天启动三次可以得到 DAU 1、启动 3。Launcher、Bridge 连接、PiP、组件重新挂载均不能重复触发这个事件。

Bomana 继续发送原有匿名日活；新的启动请求只有受限事件类型、随机事件 ID、发生时间和已声明的 Edition/展示端，不需要携带安装秘密、账号、IP 字段或游戏数据。跨日请求按首次成功接收时的 UTC 日计数，重试复用原 ID 与发生时间。建议最多补报 24 小时内的事件，允许五分钟客户端时钟超前；去重 ID 保留 30 日，过期上报拒绝，避免清理后又把旧重试计数。不建立无限离线补报队列。新增采集上线前同步更新 Bomana 隐私说明。

启动指标使用新的口径版本及明确生效日期，保留旧版启动历史原名和来源。当前数据无法准确补出 8 月 30 日以来漏掉的新式 App 启动次数，不能拿日活或网页请求数填补。界面可分别展示旧历史和新序列，不能悄悄拼成同一口径的增长曲线。

## 实现与部署范围

建议一个 Go 可执行文件、一个统计容器、每个产品一个本地 SQLite 文件。共用内部实现，保留小而固定的旧接口适配。每个数据库独立备份、独立保留期和写入锁；一个产品的汇总查询不扫描其他产品的数据。无需新增 Redis、消息队列或数据库守护进程，也不把写入挂到 Calc 的计算 worker 上。

SQLite 适用于此类单机、低到中等写入量的服务；WAL 可让读与写并行，但**每个数据库仍只能有一个写入者**，不是靠增加 Go 协程就能无限扩展。以短事务原子完成去重和计数，并限制汇总日期范围及结果大小。持久化提交成功后才能确认接收；维护任务按日期批量清理，不在每条上报里扫描整段历史。来源：[SQLite 的适用范围](https://sqlite.org/whentouse.html)、[WAL 并发与检查点](https://sqlite.org/wal.html)。Go SQLite 驱动、打包方式及内存开销尚未实测，应在隔离候选中比较后固定，不能先假设会比现有两进程之和更小。

产品身份由已配置域名/路径及内部代理决定，不由浏览器随意指定。保留 Armor 同源入口与 Bomana 现有 HTTPS 地址，通过 Caddy 转到共享服务，减少前端迁移。每个产品独立限制请求体、指标和渠道枚举、请求频率与待处理请求数；统计失败保持尽力而为，不阻塞页面、计算或启动。Origin/CORS 检查不能作为匿名上报真实无误的证明。

Armor 迁移必须继续使用现有 HMAC 与加密密钥，避免同日更换身份算法重复计数；其他产品使用独立密钥或已有匿名令牌。Bomana 数据路径完全不调用 IP 记录逻辑。跨产品只提供各自的汇总，**不声称能把 IP 日活与匿名安装日活合成为去重总人数**。

共享统计最终应有独立维护与发布入口。Armor 的普通页面发布不再打包或重启它；各产品只保留上报、展示和配置。此文暂放在现有统计实现所属的 Armor 库中，当前维护归属未改变；独立实现验收后移动维护入口并更新各产品引用，不保留多套可独立修改的实现。

## 迁移顺序与必要验证

1. 先实现兼容 Armor/Bomana 旧接口的隔离 Go 候选。使用服务器内的数据库一致性副本和合成上报，不将真实 IP、每日令牌或密钥拉到开发机或写入 Git。
2. 对全部已结束日期及渠道逐项比较旧、新公开与管理员结果。Bomana 旧接口的 `max(legacyDau, anonymousDau)`、渠道重叠和历史范围查询都要保持；不能只比较最新一天。
3. 验证重试去重、并发原子计数、UTC 跨日、进程重启、磁盘写入失败和 30 日清理。用两个产品同时请求的实测确认互不串数，并测候选 RSS、PSS、延迟与主机余量，再决定是否采用该存储实现。
4. 按产品逐个切换 Caddy 入口，切换前后只保留一个正式写入方。导入期间接收的新记录必须追平；回滚需要带回切换后新数据，不能仅恢复旧容器丢掉这段计数。旧库保留作可恢复副本，避免直接双写再相加。
5. 旧口径迁移稳定后，为 Bomana 新增已确认的启动事件，再接入 Calc。用同一浏览器当天三次成功初始化验证“日活 1、启动 3”，同时确认刷新、失败启动、渠道切换和历史显示符合各自定义。

该顺序复用现有发布与回归手段，只增加能验证数据连续性和产品隔离的测试，不扩充成通用埋点平台或另一套 CI 状态流程。
